# One C environment per Titan module

The leading follow-up design is the user's unbound foreign-import statements feeding a generated header for each Titan source module, with C symbols accessed through reserved `ffi.` and direct source imports connected by ordinary C `#include` chains. This supersedes the stricter duplicate-suppression shortlist; last-wins is a possible migration heuristic, not the leading architecture. Implicit C conversions remain an accepted FFI responsibility. This is a read-only design audit, with no implementation, compiler invocation or change to the measured baseline.

Using the existing quoted header operand, the intended shape is:

```text
foreign import "openssl/err.h"
foreign import "openssl/ssl.h"

-- C values and types use ffi.NAME throughout this Titan module.
```

## Why the large probe family disappears

Today each foreign import calls `cdriver.process_file`, which creates a fresh preprocessor context, parses a flattened header closure, and converts it into a separate `CModule`. The checker then compares ordinary names across those independently extracted graphs and queues declaration-pair probes. See [declarations.lua:604](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/checker/declarations.lua#L604), [cdriver.lua:765](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/c-parser/cdriver.lua#L765), and [declarations.lua:770](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/checker/declarations.lua#L770).

With one ordered input, include guards, macro changes, typedefs and file/prototype tag scopes are interpreted in one preprocessor/parser lifetime. A guarded declaration reached through several headers appears according to that actual combined stream, rather than once per independent extraction. Convert that result once into `ffi`; the cross-import comparison queue and its artificial redeclaration-pair probes no longer have a role. Actual conflicting C declarations remain subject to C parsing/generated-C compilation under the user's relaxed early-diagnostic contract. This does not require probe batching or a cache identity redesign.

## Order, folder modules and visibility

Use the driver's existing logical module order: folder main file first, then bytewise-sorted contributor filenames, preserving directive order within each file. All contributors share one `ffi` environment. The driver already builds one AST in that order. Relative header resolution must retain the module/source-directory rules rather than depend on an incidental generated-file location. See [driver.lua:1685](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/driver.lua#L1685), [driver.lua:1729](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/driver.lua#L1729), and [driver.lua:4000](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/driver.lua#L4000).

Make the new `ffi` namespace module-wide, including module initializers, while keeping the existing sequential restrictions on ordinary Titan imports/variables. This is an explicit simplification from per-alias import visibility. The combined input and emitted C must agree on duplicate directives: codegen currently deduplicates direct includes by rendered spelling and appends source-foreign companion headers afterward. Define that normalization once and share it. Preserve configured forced-header behavior, define dependency-header placement in the shared emission plan, and decide which compiler-private support declarations are exposed through `ffi`. See [generate.lua:158](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/coder/generate.lua#L158), [generate.lua:894](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/coder/generate.lua#L894), and [declarations.lua:1556](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/checker/declarations.lua#L1556).

## Generated module headers and direct source imports

Use a generated `A.h` as the C environment of source module A: it contains A's ordered foreign-import includes and the headers of A's direct source imports. A's generated C includes its own header. If B directly source-imports A, B's generated translation unit includes `A.h` through B's own header; this makes the same chain available to a further source importer of B. The actual filename can retain the existing `.titan.h` convention. Dependency headers must be ready before the dependent module's combined C analysis, including analysis-only/LSP runs.

There is already a partial implementation of this structure. `generate_foreign_header` emits a guarded `.titan.h` containing direct foreign includes, supplementary type-origin includes, direct source-foreign dependency headers, foreign-function declarations, and static-inline foreign bodies. It currently returns nothing unless the module contains a `TopLevelForeignFunc`. The driver similarly makes header planning/checking conditional on `ast_has_foreign_functions`. Generalize this lifecycle to source modules with a module header, including a module that merely imports foreign C declarations or only carries dependency headers. [module.lua:1121](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/coder/module.lua#L1121), [driver.lua:3530](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/driver.lua#L3530), [driver.lua:4070](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/driver.lua#L4070), [driver.lua:5269](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/driver.lua#L5269).

## What remains

One combined parse does not eliminate target-dependent questions at actual C uses: operator legality, unsafe pointer conversions, enum/carrier/range support and flexible-array extent checks remain separate. Operator and conversion probes can keep their existing individual source-keyed form. A second proposal replaces the enum-carrier candidate series with one result-bearing compilation and caches its selected carrier; see [the profiling report](../ffi-probe-profile.md#second-proposal-one-result-bearing-enum-carrier-probe). Both keep complete raw source as the cache identity. A single module-wide baseline can remain for header diagnostics in analysis-only tooling; changing that policy is separate from removing per-name redeclaration probes. Relevant entry points are [cprobe.lua:1926](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/cprobe.lua#L1926), [c_types.lua:272](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/checker/c_types.lua#L272), and [c_types.lua:1458](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/checker/c_types.lua#L1458).

`ffi` belongs to a Titan module, not the whole project. Producer-owned C types exposed through Titan source/binary interfaces still need their existing qualifiers, callback signatures, aggregate identity and origin/include metadata. The current type relation already recognizes certain named file-scope tags across producer descriptors when generated C combines their headers; do not accidentally replace that with per-module pointer identity, or broaden prototype-local/anonymous identities by spelling. See [types.lua:1764](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/types.lua#L1764). These use-site identity rules do not require restoring the old per-header redeclaration queue.

## Migration scope

Migrate bound foreign imports and their alias-qualified uses together across the standard library, compiler/runtime fixtures, examples, the language server and downstream modules. Update parser/checker/codegen tests for the new syntax, reserved `ffi`, final macro state, folder order, supported type/value projections and cross-Titan-module C values. Legacy cross-alias early-conflict expectations should be replaced according to the accepted C-compiler diagnostic contract, not preserved as a prerequisite.

The converted-FFI persistence format currently stores per-import node types, includes and the pending queue; it needs a module-environment representation and corresponding schema invalidation. Header graph entries must describe the ordered input and its complete dependency closure. This is distinct from the unchanged compiled probe source-key contract. See [foreigncache.lua:8](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/foreigncache.lua#L8) and [foreigncache.lua:77](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/foreigncache.lua#L77).

The language-server bridge currently requires `TopLevelForeignImport.localname` when extracting declarations; migrate it with the compiler AST and give the built-in namespace appropriate semantic metadata. Syntax highlighting, fixtures and saved-file hover/reference behavior also need review; completion and unsaved-buffer semantics do not follow from this proposal. [compiler_bridge.titan:2354](https://github.com/mascarenhas/vscode-titan/blob/e0bff3b6f46725880b5c8a9b7633eff82643c8a4/src/server/compiler_bridge.titan#L2354), [compiler_bridge.titan:2456](https://github.com/mascarenhas/vscode-titan/blob/e0bff3b6f46725880b5c8a9b7633eff82643c8a4/src/server/compiler_bridge.titan#L2456).
