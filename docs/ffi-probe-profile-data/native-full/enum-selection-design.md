# One compilation per enum-carrier selection

This is the second proposed optimization, alongside the separate module-header/reserved-`ffi` design. Replace the per-carrier acceptance loop with one compile-only query that returns the chosen carrier. Cache that typed result under SHA256 of the complete raw selection source. No production implementation or proof-of-concept compilation was performed.

## Captured opportunity

The native capture has 1,420 logical candidate requests, representing 138 logical selection requests. Replacing only the second `extern` declaration in each captured source with a placeholder gives 47 common source shapes across 501 physical source keys. Joining the observer's `carrier_index` and `eligible_carrier_count` batches confirms 47 complete questions after including the ordered eligible-carrier list: eight questions have nine candidates and 39 have eleven. No eligibility or carrier-metadata variant splits a shape, and each question has exactly one accepted original carrier (`int` or `unsigned int`).

With deterministic whole-query source generation and equivalent source-key reuse, those 501 compilations would become 47: 454 fewer, a 90.62% reduction in this family. The existing family took 56.171 seconds of runner time; that is not an estimate of the new implementation's time. Counts precede the combined-FFI header redesign, which can change header contexts and demand. Baseline/header-validity and other semantic probe families are outside this count.

## Preserve the current selection question

The existing checker tries a stable list of eleven primitive integer spellings. For enum types it only includes carriers whose whole range fits `lua_Integer`; enumerator-expression queries include all available carriers, then separately check the value's range if necessary. This capture's nine-carrier list excludes `unsigned long` and `unsigned long long`. Keep these eligibility semantics in the new query, with stable IDs independent of eligible-list positions. Retain the exact selected typedef/tag/expression spelling; do not replace it with the checker's guessed underlying type. ## Feasible compile-time selection and extraction

Declare the exact captured left surface once, then compare `__typeof__(&titan_probe_d)` with each eligible `carrier *` using `__builtin_types_compatible_p`. Comparing pointer types preserves pointee qualifiers that the builtin would ignore at the top level; using an address also avoids integer promotions of the enum expression. Each match is a compile-time integer expression. Sum matches and the corresponding stable IDs, then emit the count and selected ID as a small versioned `unsigned char` payload. GCC documents this compatibility builtin, and Clang explicitly supports it. [GCC builtin semantics](https://gcc.gnu.org/onlinedocs/gcc/Other-Builtins.html), [Clang builtins](https://clang.llvm.org/docs/LanguageExtensions.html#builtin-functions), [GCC typeof spelling](https://gcc.gnu.org/onlinedocs/gcc/Typeof.html).

One extraction route emits that payload as a `used` object in a dedicated section, with fixed magic, version and length. Read its bytes after successful `-c`; do not link, load, or run the target object. A byte payload avoids host-endian interpretation of a target integer field. Titan already has bounded ELF/Mach-O section parsing in `staticmetadata.lua`; factor or generalize that reader rather than requiring another `nm`/`objcopy` process. The existing reader is metadata-specific, so it is not an unchanged drop-in decoder for the new section. [staticmetadata.lua:449](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/staticmetadata.lua#L449), [staticmetadata.lua:473](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/staticmetadata.lua#L473), [staticmetadata.lua:645](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/staticmetadata.lua#L645), [Clang used attribute](https://clang.llvm.org/docs/AttributeReference.html#used).

A second route compiles with `-S` and extracts a tightly specified result marker from assembly. This avoids target-object execution and the assembler step, but requires explicit handling of assembly dialect, directives, symbol spelling and optimization. It must not infer the ID from arbitrary human-readable diagnostics. `_Generic` with the address of the declared object and pointer associations is another selection expression; the current probe command uses C99, so the documented GCC/Clang compatibility builtin is the more direct fit. Clang documents generic selections as an extension; C11 support alone should not silently change the probe dialect. [GCC compilation stages](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html), [Clang generic selections](https://clang.llvm.org/docs/LanguageExtensions.html#c11-generic-selections).

## Result and cache contract

The complete raw source must carry the ordered header environment, exact enum surface, eligible candidates, stable ID assignments, and result-format version. Hash those bytes only; retain the existing manual-clear contract for stale external compiler/header state. Store the selected carrier ID as a validated, tagged result with its schema version; a successful compiler exit alone is not a selection answer. Represent deterministic no-match/multiple-match outcomes explicitly. A successful compile with a missing, duplicated, malformed or out-of-range payload is an extraction/infrastructure failure and remains retryable. Cancellation, launch/wait/I/O failures and infrastructure compiler failure must likewise never become a cached selected carrier or deterministic semantic rejection.

A valid ID maps back to the configured profile entry and preserves the existing update of spelling, signedness, rank, width and numeric semantics. Returning an eligible-list index would be insufficient when the list changes. Keep enumerator value-range validation as its own requirement unless the complete selection source explicitly includes that predicate and the returned result distinguishes it. Future validation should cover the captured named and expression cases, typedefs/qualifiers, short enums, wide/unsigned enumerators, zero/multiple matches, result decoding and cache round trips under GCC and Clang; this note makes no unperformed validation claim.
