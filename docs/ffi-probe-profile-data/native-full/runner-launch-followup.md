# Probe launcher follow-up

The native runner does use a fork-based launch path on this Linux host. That makes process-launch work from a large server address space a concrete follow-up hypothesis. The completed capture does not measure that cost separately or establish it as the explanation for the recorded system CPU.

## What the source and binaries establish

The compiler's common `cprobe.default_runner` delegates to the configured I/O strategy. Its `probe_runner` span brackets the whole strategy call, including result normalization; it is not a span around GCC alone. See [cprobe.lua:731](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/cprobe.lua#L731) and [runner observer patch](../../../scripts/profiling/patches/titan-observer.patch).

In the native embedded-Lua server, `CompilerIO:run` validates argv, prepends locale assignments, and launches `/usr/bin/env` with an argument array. `capture_process` starts separate reader and process-wait Tasks before its first suspension, closes stdin, and joins both. The result includes the whole spawn/drain/reap wall interval. This is cooperative event-loop waiting, with no polling loop in the compiler adapter. See [compiler_io.titan:687](https://github.com/mascarenhas/vscode-titan/blob/e0bff3b6f46725880b5c8a9b7633eff82643c8a4/src/server/compiler_io.titan#L687), [compiler_io.titan:790](https://github.com/mascarenhas/vscode-titan/blob/e0bff3b6f46725880b5c8a9b7633eff82643c8a4/src/server/compiler_io.titan#L790), and [compiler_io.titan:827](https://github.com/mascarenhas/vscode-titan/blob/e0bff3b6f46725880b5c8a9b7633eff82643c8a4/src/server/compiler_io.titan#L827).

`system.spawn` reaches `uv_spawn` synchronously before returning the process handle. Successful process waiting then suspends through the existing libuv process callback; libuv reaps with `waitpid`, and the Titan callback publishes the result and resumes its waiter. See [process.titan:858](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan/uv/process.titan#L858), [process.titan:344](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan/uv/process.titan#L344), and [process.titan:942](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan/uv/process.titan#L942).

The pinned libuv 1.52.1 Unix source calls `fork()` on the Linux route, then the parent reads an exec-status pipe until the child execs or fails. Its alternative `posix_spawn` route is guarded by `__APPLE__`. This is also present in the preserved measured executable: disassembly of `uv_spawn` calls `fork@plt` at `0xf47bc2`, `read@plt` at `0xf47c2c`, and child `execvp@plt` at `0xf48142`. See [libuv process.c:841](https://github.com/libuv/libuv/blob/v1.52.1/src/unix/process.c#L841) and [process.c:871](https://github.com/libuv/libuv/blob/v1.52.1/src/unix/process.c#L871).

The standalone Lua compiler uses `Sync:run`, which invokes `io.popen` on a quoted shell command, reads the complete output, and closes the pipe to collect status. Installed Lua's POSIX implementation delegates to libc `popen`/`pclose`. This host has glibc `2.43-8.fc44`; local libc disassembly shows `_IO_proc_open` calling `posix_spawn` at `0x5e606`. Thus the standalone and native transport mechanisms differ. Their workloads and ccache controls also differed, so the observed duration difference cannot isolate the transport effect. See [io.lua:447](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/io.lua#L447) and [liolib.c:58](https://github.com/lua/lua/blob/v5.5.1/liolib.c#L58).

## Hypothesis and its limits

The native probe-runner intervals contain 1,239.624 s wall, 344.320 s parent process CPU, 357.874 s reaped-child user CPU, and 532.743 s reaped-child system CPU. The ready snapshot reports a peak RSS of 19,574,208 KiB, approximately 18.667 GiB. Neither counter identifies time in the spawn call, memory at each spawn, faults, or kernel functions.

Linux fork uses copy-on-write memory and duplicates page tables; it does not eagerly copy every resident byte. Repeated duplication of a large parent's page tables and disposal of inherited mappings at exec are therefore plausible costs. Actual copy-on-write faults, libc fork preparation, process setup, compiler/assembler system calls, and callback/pipe work are other possibilities. The measured child-system total cannot distinguish them, and the end-of-run RSS high-water mark does not establish the size of the parent during every probe. [Linux fork documentation](https://man7.org/linux/man-pages/man2/fork.2.html).

## Exact next measurement

In a separate disposable diagnostic run, first split the existing physical runner into two measured intervals: immediately before/after `system.spawn` returns, then spawn return through the joined output/wait completion. Keep the existing execution ID and raw-source key, and record parent user/system CPU separately, minor/major faults, and `/proc/self/status` values `VmRSS`, `VmSize`, and `VmPTE` at the spawn boundary. Use a bounded sample of early, middle, and late probes with the same controlled compiler and cache state; record sampling overhead separately.

Then obtain a short process-tree syscall trace around the same sample for `clone`, `clone3`, `fork`, `vfork`, `execve`, and `wait4`/`waitid`, including syscall durations and PIDs. That establishes how much latency is before exec and whether it grows with the parent's mappings. If launch or exec dominates, use a kernel CPU call-stack profile of that bounded sample to distinguish page-table copying, inherited-mapping teardown, COW faults, allocator/fork hooks, and ordinary compiler system calls. Correlation with RSS alone is insufficient. `strace` and `perf` were not on this task's current PATH, so tool availability must be arranged for that later diagnostic environment.

No process experiment, compiler invocation, implementation change, or production setting change was performed for this follow-up.
