# Repeated declaration suppression: semantic review

This is a read-only next-experiment recommendation against the frozen compiler based on `788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d`. No optimization, test execution or compiler invocation was performed. The pilot's same-origin, identical-rendered function/typedef keys identify a useful investigation group; they do not prove eligibility for suppression.

## Why the existing exception is narrow

The ordinary relation compares qualifiers, adjusted function signatures, ABI, typedef targets and nominal aggregate identities. It distinguishes `exact` from target-C-dependent `conditional` cases such as old-style prototypes, anonymous aggregates and symbolic array bounds. See [foreigntypes.lua:392](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/foreigntypes.lua#L392).

`source-repeat` is a correctness exception for independently extracted **prototype-local tags**. Two import closures can extract the same guarded declaration into fresh tag objects; synthesizing its prototype twice invents two prototype scopes. The exception requires ordinary compatibility to have failed, matching physical declaration source, and a relation permitting only explicitly marked prototype-local tag differences. That relation checks the aggregate graph and a bidirectional tag mapping, and requires an actual prototype-tag match. See [declarations.lua:780](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/checker/declarations.lua#L780), [foreigntypes.lua:170](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/foreigntypes.lua#L170), and [foreigntypes.lua:434](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/foreigntypes.lua#L434). Its acceptance still requires the final ordered-header C baseline.

The baseline validates the actual cumulative translation unit, including conflicts the isolated parser may collapse. Synthetic pair probes additionally validate the spellings/types extracted independently; the source comment explicitly says the baseline alone is weaker. A pair can fail rendering even when its two graph roots are identical. See [c_types.lua:817](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/checker/c_types.lua#L817), [cprobe.lua:486](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/cprobe.lua#L486), and the [unspellable anonymous-pair regression](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/spec/cprobe_spec.lua#L770).

## A concrete failure of source identity alone

Consider these headers, as an **unexecuted reasoning example**:

```c
/* prelude.h */
#define HIDE_DECL 1

/* common.h */
#if !defined(HIDE_DECL) && !defined(COMMON_H)
#define COMMON_H
typedef int ffi_hidden_alias;
extern ffi_hidden_alias ffi_hidden_function(void);
#endif

/* left.h and right.h each contain: */
#include "common.h"
```

Import `prelude.h`, `left.h`, then `right.h`. Independently parsed left/right closures can both expose the same physical typedef/function with identical extracted types. The final ordered preamble suppresses both declarations and can still compile. The existing typedef pair renders `extern ffi_hidden_alias titan_probe_d;` twice, but that typedef name is absent in the final context, so pair validation rejects. The function pair also retains that missing return-type spelling. Typedef rendering preserves the alias name except for the specific declaration-owned array view: [cdeclarator.lua:487](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/cdeclarator.lua#L487), [cprobe.lua:477](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/cprobe.lua#L477).

This differs from equal structural targets: final identifier visibility matters. Existing tests cover closely related hazards: [same-source macro-dependent type changes](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/spec/checker/c_ffi_declaration_compatibility_spec.lua#L1365), [exact repeats changed by cumulative macro state](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/spec/checker/c_ffi_declaration_compatibility_spec.lua#L1961), and [distinct macro-suppressed anonymous aliases](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/spec/checker/c_ffi_declaration_compatibility_spec.lua#L1985). The exact hidden-typedef example above is a proposed additional regression, not a claim that an existing test covers it.

## A bounded next experiment

Investigate a separate **post-baseline suppression decision for originally exact repeated functions/typedefs**, with conservative fallback to the unchanged individual probe. Preserve every per-header member/type namespace and every pending declaration's original classification. Do not suppress import conversion or erase candidate origins.

Matching normalized preprocessed declaration tokens plus an established single emission in the final ordered preamble would be stronger evidence than a source location or a syntactic include guard. To support suppression, the witness must come from the actual ordered preprocessing context and match both independent extractions. Normalization should remove only irrelevant whitespace/comments, retaining identifiers, qualifiers, declarator structure and array syntax. Matching text must also preserve the referenced typedef/tag bindings and scope; spelling alone does not establish C type identity. A header merely containing a guard is insufficient because a later wrapper can undefine it.

Such a witness could establish that two namespace entries describe one actual declaration and that the global baseline already accepted that declaration. It would not justify deleting either namespace entry. It would also not automatically establish that the existing synthetic pair is renderable under final macro state: the experiment must retain render checks and examine final macro substitution/identifier visibility, including the generated probe identifier. The reconstructed macro map in [symtab.lua:186](https://github.com/mascarenhas/titan/blob/788b353bed8e2580bbf12bf8ebf4ad9e7f1ab47d/titan-compiler/symtab.lua#L186) is useful input, but is not by itself a recorded final C emission/binding witness. The current capture lacks that complete witness, so no number of safely removable keys can yet be reported.

Start with exact prototype functions whose rendered signature uses a closed set of ordinary scalar/void/pointer forms. Exclude typedef spellings, aggregate/tag types, old-style forms, array paths and declaration-owned composite views from this first eligibility measurement. Extending to the dominant typedef/named-type group would then require the explicit final binding/visibility witness above. In every stage, preserve compiler-option and synthetic-declaration diagnostic behavior; neither identical text nor the existing `exact` relation proves that arbitrary configured diagnostics will accept a redundant synthetic declaration. This is an experiment boundary, not a proven fast path.
